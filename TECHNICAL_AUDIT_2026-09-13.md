# Rent Aggregator Baku: аудит 13 сентября 2026

## Статус

Диагностика продакшена выполнена без изменений сервера. Подготовлены локальные исправления, **не развёрнуты**. Система не признана автономной или готовой: отсутствуют worker-контейнеры, не завершены испытания восстановления, сквозная проверка Telegram и наблюдение.

Проверены активный код в контейнере, PostgreSQL, настройки webhook, текущий GitHub workflow, последние 100 запусков, annotations и traceback трёх последних сбоев, соответствующие уведомления Gmail. Прочитаны текущий и майский контексты, README, серверные инструкции, основные серверные и сборочные модули, тесты. В доступном списке задач единственная задача непосредственно этого проекта — текущая. Прочитан контекст соседней задачи «Начальник», но её пустые последние turn summaries не дают оснований приписывать ей остановку worker'ов. Все прежние заявления о работоспособности рассматриваются как исторические.

## Почему остановилась доставка

В `docker ps -a` присутствуют только `rent-aggregator-baku-app-1` и `rent-aggregator-baku-postgres-1`, оба healthy. Контейнеров `channel-worker` и `private-worker` нет даже среди остановленных. При этом `docker compose config --services` активного release перечисляет оба worker-сервиса. Это непосредственная причина отсутствия доставки после приёма данных.

**Кто и какой командой удалил worker'ы, не установлено.** Нельзя утверждать, что это был crash, OOM, Github или соседний проект: отсутствует подтверждающий журнал события удаления.

## Архитектура следующего этапа

Сохранить PostgreSQL, отдельные app/private/channel процессы, собственные секреты/тома/лимиты проекта. Traefik — маршрутизатор TLS, **не** очередь, планировщик, реплика БД или гарантия отказоустойчивости. Общая среда и другие боты не изменялись.

Рекомендуемый сбор: отдельный процесс в нашем проекте, цикл 60–120 секунд, persist всех найденных ID до загрузки деталей, курсоры покрытия по источнику/категории/городу, метрики незавершённого обхода, обратное давление и остановка при challenge. GitHub оставить для CI/deploy, либо признать пяти минут недостижимыми при сохранении нынешнего расписания. Оценка дополнительной платы за размещение на имеющемся сервере: **0 при наличии свободных ресурсов**, но CPU/память/нагрузка требуют нагрузочного теста; это не предложение тарифного плана провайдера. HA потребует второй независимый узел и отдельно согласованный бюджет.

Доставка: короткая транзакция claim с attempt_id/lease → commit → Telegram → короткая фиксация результата. Потерянный ответ или crash после send переводится в `uncertain`, без автоматического повторного send до сверки. Невозможно одновременно обещать exactly-once и безусловное автоматическое восстановление там, где внешний API не предоставляет идемпотентную отправку. ID сообщения сохранять при подтверждении, данные объявления хранить в корневой записи/версиях, а не размножать в журнале доставок.

Отдельный versioned event log для фильтров, нормализованных фактов и решений доставки; `observed_at`, `source_updated_at`, `source_created_at` (nullable + provenance), `queued_at`, `attempt_started_at`, `sent_at` — разные поля. Версии должны позволять объяснить каждое включение/исключение. Для неизвестной даты публикации отдельная политика, а не подстановка фото.

Мониторинг: возраст последнего успешного обхода и ingest, покрытия курсоров, heartbeat каждого worker, oldest eligible pending, failed/dead_letter/uncertain, 403/429, p50/p95 доставки от observation, количество публикаций по политике, дата последней проверенной резервной копии. Healthy HTTP сам по себе недостаточен. Оповещения при изменении аварийного состояния, не спам при каждом цикле.

## Резервная копия и откат

Снимок на компьютере: `backups/audit-20260913T0210/database.dump`, **56 937 494 байта**, SHA-256 `eae53ede69684bdb0c3b4b83e440f8b96f8ce49e304ed4f7b529cbf10f994d90`. Дамп streamed через SSH, на сервере резервный файл не создавался. Каталог прочитан `pg_restore --list`, сохранены manifest, агрегированная диагностика и активные четыре серверных модуля. ACL папки ограничен владельцем Windows и SYSTEM; sandbox-аккаунт больше не читает её без повышения прав.

**Полное восстановление не проверено.** `--list` подтверждает читаемость каталога, не данных и связей. Локальные PostgreSQL/Docker не обнаружены. До production cutover нужен отдельный PostgreSQL 16, восстановление с `--exit-on-error`, сравнение counts/FK/уникальностей и тесты очереди. Текущий backup не делает деплой автоматически разрешённым. Нельзя автоматически восстанавливать старую БД поверх накопленных пользователей/аудита.

Попытка повторно проверить каталог старого августовского дампа через серверный `pg_restore` заблокирована auto-review: это передача полного чувствительного дампа обратно на сервер. Повторной попытки/обхода не было; проверка старого архива не выполнена. Для restore-теста на сервере требуется явное разрешение на передачу выбранного локального дампа в изолированный тестовый контейнер. Предпочтительная альтернатива без передачи данных — локальный PostgreSQL.

Откат приложения: остановить только собственные worker-сервисы, вернуть зафиксированную версию нашего app/кода, оставить доставку выключенной, проверить схему и доступность. Общие Compose/Traefik не трогать, CENTRAL_INGEST_URL не удалять. Аддитивную миграцию dead_letter нельзя откатывать удалением задач. Восстановление всей БД — отдельная согласованная аварийная процедура.

Пока компьютер выключен, текущая политика локальных копий не создаёт новые backups: RPO растёт. Для автономных копий нужно либо постоянно включённое резервное устройство, либо отдельное зашифрованное внешнее хранилище. Не добавлялось без согласования.

## Проверка и оставшаяся работа

Локально 24 unittest проходят, `compileall` и `git diff --check` проходят. Проверены парсер диапазонов, UI-генерация трёх языков и лимиты callback bytes, политика канала, неизвестные поля, 403/429, redaction, fail-closed и конфликт idempotency. Это **не** PostgreSQL integration test и **не** реальная доставка Telegram.

Не выполнены: изолированное восстановление; SQL/worker crash-тесты; тест сообщения, принятого Telegram с потерянным ответом; нагрузочное совместное испытание UI и доставки; полный E2E регистрации/админ-доступа/редактирования/удаления фильтров; повторная проверка всех форм источника; полный исторический coverage сайта; deployment; семидневное наблюдение. Сохранённые unit-тесты не заменяют эти пункты.

| Требование ТЗ | Результат |
|---|---|
| Архитектура и контекст | ключевой runtime сопоставлен; исторические документы помечены |
| Причина остановки | отсутствие worker подтверждено; происхождение удаления не установлено |
| Корректность и объём | DB-аудит выполнен; полнота сайта и правила на дату отправки недоказуемы без истории |
| Пять минут | текущие измерения опровергают; нужен выбор способа сбора |
| Надёжность/безопасность | локальный пакет исправлений; critical recovery/ledger/uncertain ещё остаются |
| Фильтры RU/AZ/EN | локальный кандидат диапазонов и подтверждения backfill; Telegram E2E ожидает согласования |
| Границы | сервер/общая среда/пользовательские рассылки не менялись |
| Готовность | не достигнута; требуется следующий этап и семь дней наблюдения |

## Решения владельца

1. Канал: рекомендуем **помесячную аренду квартир в Баку**, посуточную оставить в личных подписках. Это продуктовый выбор, не технический лимит; текущая политика daily ещё не менялась.
2. Накопленные 2519 публикаций: рекомендуем сохранить в журнале, **не рассылать**, после согласованного времени включать только новые задачи; старые removal отдельно проверить. Без разрешения ничего не списываем.
3. Для цели пяти минут рекомендуем разрешить **отдельный сборщик внутри нашего проекта на сервере**, GitHub оставить CI. Общую инфраструктуру не менять.
4. Разрешить временный изолированный PostgreSQL для restore/интеграционных тестов? Рекомендуем ограниченный одноразовый контейнер с отдельными именами/сетью, без подключения к соседним ботам; после проверки удалить только его тестовые данные. Альтернатива — установить локальный PostgreSQL. Пока ни один вариант не запускался.
5. После исправления критических рисков разрешить тестовые сообщения только администратору и затем **семь дней наблюдения**? Общая рассылка пользователям и публикация архива остаются отдельным разрешением.
